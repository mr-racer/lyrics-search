# Новый ИИ-ассистент: лабораторная архитектура + смена эмбеддера

Дата: 2026-08-09. Ветка: `genius-addition`.

## Что делаем и чего не делаем

Две несвязанные вещи в одной сессии.

**1. Прод — ровно одна правка.** `Qwen/Qwen3-Embedding-0.6B` → `Octen/Octen-Embedding-0.6B`
в `ModelRegistry`. Больше в `app/` ничего не меняется: боевой ассистент, боевой
веб-поиск и боевой `facts_retrieval.py` остаются как есть.

**2. Лаба — новый ассистент целиком.** Пакет `lab/agent/`, который автор крутит из
ipynb на отдельной машине, обращаясь к LLM и SearXNG на сервере по сети. Каталог
библиотеки — локальный дамп прод-базы `cache/metadata.db`, путь задаётся из ноутбука.

Явно вне объёма: перенос нового веб-поиска или нового ретрива фактов в прод (будет
отдельной сессией), CLAP-фильтрация по стилю (LLM только извлекает стиль, ветку автор
доделает сам), фронтенд.

> **Поправка по ходу реализации (2026-08-09).** Изначально спека предполагала
> корневой пакет `retrieval_core/`, общий для лабы и переписанного боевого
> `app/services/facts_retrieval.py`. Владелец уточнил объём: прод трогаем только
> сменой модели, новый ретрив фактов живёт в лабе. Поэтому переносимая часть
> лежит в `lab/agent/retrieval/` (никаких импортов из остального `lab`),
> а `app/services/facts_retrieval.py` и `facts_index.py` не тронуты. Ниже
> Части 1 и 3 приведены к фактическому состоянию.

## Часть 1. Смена эмбеддера в проде

Octen-Embedding-0.6B: **dim 1024** (совпадает с Qwen — геометрия коллекций не меняется),
контекст 32k, `prompts = {"query": "Instruct: Given a web search query, retrieve relevant
passages that answer the query\nQuery:", "document": " "}`.

Правки в `app/resources/model_registry.py`:

- `TEXT_MODEL_NAME = "Octen/Octen-Embedding-0.6B"`, `VECTOR_DIM` остаётся 1024.
- `tokenizer_kwargs={"padding_side": "left"}` при загрузке.
- Ручной `QUERY_PREFIX` уходит. Обе стороны кодируются собственными промптами модели:
  `encode_text(..., is_query=True)` → `prompt_name="query"`, документная сторона →
  `prompt_name="document"`. Сейчас документы кодируются вообще без префикса; у Octen
  документный промпт непустой (пробел), и рассинхрон стоит полноты выдачи. Наличие
  `prompts` проверяется кодом один раз при загрузке — если модель их не везёт, работает
  прежний путь с явным префиксом.
- `MAX_SEQ_LENGTH` остаётся 2048 при окне 32k: самый длинный дедуплицированный текст в
  библиотеке ~1900 токенов, а полное окно означало бы кодирование лирики целиком.

**Миграция (одно окно обслуживания, на прод-сервере):**

1. `python -m scripts.migrate_dense --dry-run` — отчёт.
2. `python -m scripts.migrate_dense --yes` — переливка всех `acct_*`.
3. Дроп всех `facts_acct_*`.

Шаг 3 обязателен и добавляется в `migrate_dense`: в этих коллекциях лежат квеновские
вектора фактов, а запрос после смены модели кодируется Octen'ом — сравнение шло бы между
разными пространствами и молча возвращало мусор. Коллекции заполняются по требованию, так
что дроп восстанавливается сам при первом же вопросе о субъекте.

До прогона миграции текстовый поиск на проде нерабочий. Выкатка — одним заходом (на
GPU-хосте лимит на частые SSH-подключения).

Документация: упоминания модели в `CLAUDE.md` (секция Models) обновляются.

## Часть 2. `lab/agent/` — структура

```

  config.py        AgentConfig: адреса, пороги, бюджеты, веса
  models.py        контракты (dataclasses): SearchHit, Page, Chunk, TrackRef,
                   ResolvedTrack, Plan, Filters, Evidence, GeneralResult, PlaylistResult
  events.py        EventSink — тот же NDJSON-протокол, что в проде (sync + async колбэк)
  llm.py           LLMClient: OpenAI-совместимый chat + строгий разбор JSON + один ремонт
  prompts.py       все промпты, с проработанными примерами
  planner.py       шаг планирования + валидаторы (вся проверка — в коде)
  clarify.py       расшифровка аббревиатур: гипотеза → пользователь → !wp → сдаёмся
  catalog.py       LibraryCatalog поверх SQLite track_metadata
  fetch.py         PageFetcher: websearch_lab.md() + кэш по URL + параллель
  sources.py       SearchSources: web / wikipedia / apple / fandom + rerank_hits
  chunking.py      MarkdownChunker (context-aware, путь заголовков внутри чанка)
  tables.py        markdown-таблица → TrackRef по заголовкам колонок
  extraction.py    структура (Apple/таблицы) + TrackExtractor (LLM для прозы)
  reasons.py       порт reason_gate: отсев причин-заглушек
  pipeline.py      Assistant + GeneralBranch + PlaylistBranch
  retrieval/       ← подпакет, который потом переносится в прод целиком
    __init__.py    HybridRetriever (+ extend: доиндексация без переэмбеддинга)
    types.py       Ranked, Fact — здесь, чтобы подпакет ни от кого не зависел
    hub.py         ModelHub: ленивые синглтоны dense / sparse / cross-encoder
    bm25.py        BM25Okapi своей реализацией (новая зависимость не нужна)
    facts.py       FactSource + SqliteFactSource + FactsRetriever
```

`retrieval/` не импортирует ничего из остального `lab/` и зависит только от
torch / transformers / sentence-transformers / numpy. Это условие переносимости: порт в
прод = перенос папки плюс ~40 строк обвязки в `app/services/facts_retrieval.py`.

Тяжёлые импорты (torch, transformers, trafilatura, lxml) — только внутри функций. Это
позволяет тестировать чистую логику там, где моделей нет, и повторяет правило прода.

## Часть 3. Ретрив: один стек на два применения

`HybridRetriever(docs: list[str])` — три сигнала, слияние, реранк:

1. **dense** — Octen, `prompt_name="query"` для запроса, `"document"` для документов;
2. **sparse** — MILCO (`omai-research/milco-650m`, `trust_remote_code=True`),
   `encode_query` / `encode_document`, `source_view=True`;
3. **bm25** — по фолдингу и простой токенизации.

RRF (k=60) с весами `{dense: 1.0, milco: 1.0, bm25: 0.3}`, затем кросс-энкодер
`BAAI/bge-reranker-v2-m3` по всем кандидатам, `final = 0.8·p + 0.2·rrf_norm`, отсечка
`p ≥ 0.2` (единый порог для всех вызовов CE в пайплайне, подбирается опытом позже).

Псевдо-релевантной обратной связи здесь нет. Она была костылём под ситуацию «русский
запрос против английского документа, а BM25 — единственный лексический сигнал»;
кросс-языковую работу теперь делают MILCO и Octen, а BM25 идёт третьим с весом 0.3.

Деградация: любая модель не поднялась — лог и ранжирование одним BM25. Ретрив не бросает
исключений наружу никогда.

**Применение А — факты (`retrieval/facts.py`).** Пул кандидатов: ВСЕ сырые факты субъекта
(песня и её артист) из SQLite `song_facts` / `artist_facts`. Без фильтра по длине, без
обрезки текста, без Qdrant. Дедуп идентичных строк. Отбор — только по порогу CE, без
ограничения по количеству; размер пачки и её длина в символах логируются.
Источник хранилища инжектируется (`FactSource` — один метод), поэтому при переносе в
прод `MetadataDB` подключается адаптером в четыре строки, а не переписыванием модуля.

**Применение Б — чанки веб-страниц (`retrieval.py` в корне пакета).** Один ретривер на
ВСЕ чанки всех страниц итерации, накопительно между итерациями, дедуп по `(url, hash
чанка)`. Запрос — отдельный «раскрывающий» запрос от LLM, без года и прочих фильтров.
Берём до 10 чанков выше порога.

## Часть 4. Планировщик — что решает модель, что проверяет код

Один вызов LLM возвращает JSON. Код проверяет каждое поле и вправе выбросить любое:

| поле | проверка в коде |
|---|---|
| `intent` | только `general` или `playlist`, иначе переспрос |
| `era` | нормализуется в `(lo, hi)`, границы 1900…2027 |
| `style` | обязан быть подстрокой запроса пользователя после фолдинга, иначе выбрасывается — так «извлекаем AS IS, не выдумываем» становится проверяемым |
| `title` (фильм/игра) | либо присутствует в запросе, либо помечен как расшифровка и уходит в clarify |
| `artist`, `song` | сверяются с библиотекой через `LibraryCatalog` |
| `web_queries` | ровно 2, непустые, дедуп между итерациями |
| `ce_query` | ровно 1 |
| `allowed_tools` | **проставляет код** по intent; модель на это не влияет |

Кавычки вокруг найденной сущности навешивает код, а не модель. Требование «искать
по-английски» живёт в промпте; кода-принуждения нет — русский запрос в SearXNG тоже
работает.

## Часть 5. Расшифровка аббревиатур (`clarify.py`)

«музыка из GTA 5» → `Grand Theft Auto 5`. Порядок:

1. LLM предлагает расшифровку с уверенностью;
2. политика из конфига: `auto` (принять), `ask` (спросить через колбэк), `wiki` (сразу к
   шагу 3). В ноутбуке по умолчанию `auto`, в проде это станет `clarify`-фреймом на фронт;
3. если отбито или неизвестно — запрос в SearXNG с движком только `wikipedia`, заголовок
   первого результата фетчится и подставляется вместо аббревиатуры;
4. если и там пусто — результат `needs_user_input` с извинением и просьбой вписать
   название вручную.

`Assistant.run()` принимает `on_clarify: Callable[[ClarifyRequest], Awaitable[str | None]]`.
Конвейер приостанавливается на этом колбэке — та же форма, что понадобится на фронте.

## Часть 6. Ветка «общий вопрос»

Параллельно: факты субъекта из библиотеки (Применение А) и два потока веба —
Wikipedia через движок `wikipedia` и общий SearXNG (20 результатов).

Общий поток: `title + snippet` каждого результата → кросс-энкодер с `ce_query` → выжившие
`p ≥ 0.2` → фетч через `PageFetcher` → чанкинг → Применение Б → до 10 чанков.

Факты и чанки складываются в **один нумерованный pack**. LLM возвращает
`{answer, used: [n...], sufficient, missing, next_queries}`.

**Решение об ещё одной итерации принимают вдвоём, и право вето — у кода:**

- модель сказала «достаточно», но максимальная CE-вероятность ниже порога → итерация
  всё равно будет: модель не видит чисел и склонна принять любой текст за ответ;
- модель сказала «мало», но бюджет исчерпан или прошлая итерация не принесла ни одного
  нового чанка → итерации не будет, отвечаем тем, что есть;
- «раскрыт ли вопрос по существу» — суждение, и его выносит только модель. Код такого
  не умеет и не притворяется.

Максимум 2 итерации по умолчанию.

Проверка цитат: пустой `used`, индексы вне диапазона или пустой ответ — ответ
выбрасывается целиком, пользователь видит нумерованный pack. Ненумерованный абзац
физически не может дойти до пользователя.

## Часть 7. Ветка «плейлист»

Три источника, разные пути:

1. **music.apple.com** — поиск с ограничением по хосту, фильтр хоста в коде,
   `parse_apple_playlist(html, url)` даёт структуру. Ноль LLM. Берутся только
   редакторские плейлисты (`author` начинается с «Apple Music»);
2. **Wikipedia / Fandom** — `.md()`, затем `tables.py` разбирает markdown-таблицы **по
   заголовкам колонок** (Title/Song/Track/Name, Artist/Performer/Composer, Year). Это
   разбор структуры, а не эвристика по тире. Таблицы идут мимо реранка целиком и сразу
   матчатся с библиотекой — саундтрек на 200 строк маленькая модель не перепишет;
3. **общий веб** — тот же путь, что в общей ветке (CE по сниппетам → фетч → чанки →
   CE), и LLM извлекает `{title, artist}` только из прозы и листиклов.

**Отбор — код, не модель.** Каждый кандидат копит вес по источникам: wiki/apple = 2.0,
остальное = 1.0. Год: из библиотеки, если трек найден; иначе со страницы; неизвестен —
оставляем (в интернете считаем написанной правду). Резолв против библиотеки — строгий
exact (фолдинг, снятие feat) → fuzzy с жёстким порогом, каждый результат помечен
`exact`/`fuzzy`/`none`.

**Декомпозиция при недоборе.** Цель — `count` из запроса пользователя, если он его
назвал, иначе 15. Если после фильтров набралось меньше 60% цели, констрейнт снимается из
текста запроса и применяется постфактум фильтром. Максимум два послабления, потом отдаём
что есть. Итераций поиска в этой ветке максимум 3.

Финальный список собирает код по `track_id`; галлюцинированный идентификатор пройти не
может. LLM только упорядочивает и пишет причины — причины-заглушки отсекаются проверкой,
как в боевом `reason_gate`.

## Часть 8. Что переносим из текущего ассистента

Переносим: дизамбигуацию субъекта (тонкий зазор между кандидатами → карточки выбора,
не догадка), слоты и стики-фоллоапы (`last_artist` / `last_song` / `last_intent`;
сущности тянет планировщик, валидирует код), `JUNK_URL`, детерминированный
фоллбэк-ответ, нумерованный pack с проверкой цитат, «молчание — валидный ответ»,
лимиты поисков и дедуп запросов, сборку треклиста кодом, строгий резолвер, NDJSON-события.

Не переносим: GLiNER2 (и в роутинге, и в экстракции песен), `tracklines()` /
`parse_track_line()` (эвристики по тире), таблицу `AUTHORITY` (её работу делают CE и
разделение потоков), PRF, tool-calling в основном контуре.

## Риски

1. **Смена эмбеддера необратима без миграции.** До прогона `migrate_dense` поиск по
   библиотеке отдаёт мусор. Дроп `facts_acct_*` в том же окне обязателен.
2. **Отсутствие капа на факты — решение автора.** При щедром пороге 0.2 у артиста с
   двумя сотнями фактов в промпт уедет всё прошедшее; это ровно тот режим «перескажи
   весь список», против которого ветка и писалась. Размер пачки логируется, чтобы было
   видно, происходит ли это на самом деле.
3. **+2.4 ГБ VRAM** на лабораторной машине: MILCO ~1.3 ГБ и кросс-энкодер ~1.1 ГБ
   (Octen встаёт на место Qwen). Все три резидентно; если тесно — кросс-энкодер
   переводится в ленивую загрузку одной строкой конфига.
4. **MILCO требует `trust_remote_code=True`** — исполняется код с Hugging Face. Для
   лабы приемлемо; при будущем переносе в прод это решение нужно принять осознанно.
