# Биография артиста: один путь вместо двух

Дата: 2026-08-26 · Ветка: `genius-addition`

## Что не так сейчас

Биографию пишут **две независимые ветки**, и вторая ничего не знает о первой.

`ai_tasks/artist_bio.py` сначала зовёт `bio_v2.build` (детерминированный
конвейер по статье Википедии), а если тот вернул пустой текст — зовёт
`llm_web_search.web_research_bio`, агента на pydantic-ai, который сам решает,
что искать. На проде это **104 биографии из 580** (`artist_bios`, коллекция
`acct_c2b5b12d…`): 476 написаны по статье, 104 — агентом.

Ветки различаются не только промптом:

| | bio_v2 | агент |
|---|---|---|
| клиент SearXNG | `SearchSources` → `resources/searxng_client` | свой `httpx.get` (`llm_web_search.py:473`) |
| пул кандидатов | 20 + CE-гейт по `title+snippet` | `max_results=3`, без гейта |
| фильтры | `JUNK_URL`, спам-хосты, host-takeover, дедуп | нет |
| фоллбэк движка | нет | прямой DDG |
| пауза между запросами | `_pace(1.5 s)` | нет |
| контроль текста | полный `tq.check(source=…)` | без `invented` — сверять не с чем |

Плюс три отдельные проблемы бюджета:

1. **Лестница проб стоит 9–10 HTTP на артиста.** `mediawiki.probe_titles`
   делает отдельный запрос на каждый дизамбигуатор (`(band)`, `(musician)`,
   `(singer)`, … — 8 для en, 12 для ru) и брейкается на первом попадании; всё
   это повторяется для второго языка, следом до 4 полнотекстовых `search`.
   Замерено на проде: 9–10 запросов, и это нижняя оценка.
2. **`widen` тратит до 4 веб-поисков на артиста** — по одному на пустой фасет,
   каждый тянет ещё до 2 страниц.
3. **Бюджет `SearchSources` не работает вовсе.** `artist_bio._web_rows`
   создаёт `SearchSources(AgentConfig())` заново на каждый вызов, а счётчик
   `self.searches` и дедуп повторных запросов живут в экземпляре. Константа
   `max_web_searches = 8` не ограничивает ничего.

Суммарно на одного артиста в худшем случае: ~20 обращений к API вики,
до 8 поисков в SearXNG (5 в bio_v2 + 3 у агента) и до 18 загрузок страниц.

## Целевая форма

Одна ветка. Веб перестаёт быть отдельным конвейером и становится **вторым
источником в том же корпусе**. Всё, что ниже сбора источников, не знает,
откуда пришли чанки.

```
collect_sources(artist)                          бюджет: 3 запроса
  ├─ WIKI (2 HTTP, только want-язык)
  │    [1] батч-проба заголовков → CE-гейт → статья?
  │    [2] полнотекстовый поиск  → CE-гейт → статья?
  │    └─ есть → fetch → чанки
  └─ WEB (1 поиск, только если из вики чанков не вышло)
       SearchSources.web(…) → junk/спам → CE-гейт по title+snippet
                            → fetch ≤3 страниц → CE-гейт по телу → чанки
       + чанк из AudioDB-сида
                       ↓
              один корпус → HybridRetriever
                       ↓
   write_bio (5 граней, RRF)        read_facets (ретрив, БЕЗ поиска)
```

### Ступень WIKI — ровно 2 HTTP

`mediawiki.probe_titles` заменяется на `probe_titles_batch(name, lang)`: один
запрос с `titles="Merk (band)|Merk (musician)|Merk (singer)|…"`. MediaWiki
принимает список заголовков в одном вызове; для `prop=extracts` нужен
`exlimit=20` вместе с `exintro=1` (по умолчанию `exlimit=1`).

> **Проверено живым запросом 2026-08-26.** `exlimit=20` принимается без
> warnings; en (8 заголовков) вернул `Merk (musician)` с extract на 318
> символов, ru (12 заголовков, RU+EN суффиксы) — тоже одним запросом.
> Фоллбэк на `prop=pageprops` без extracts не понадобился.

Порядок ответа API произвольный, и заголовок может уехать по редиректу или
нормализации — ответ сопоставляется с запросившим суффиксом через
`query.normalized` и `query.redirects`, иначе `(band)` перестанет выигрывать у
`(singer)`, а статья под каноническим именем («Aria (band)» → «Aria (Russian
band)») просто потеряется.

Возвращаются ВСЕ попадания, а не первое: запрос уже оплачен, и гейт судит, кто
из них этот артист, лучше, чем порядок суффиксов.

`article.find` схлопывается до двух ступеней на **одном** языке
(`preferred_lang`): батч-проба → гейт → полнотекстовый поиск → гейт. Циклы
по языкам и по суффиксам уходят. Последняя ступень `site:*.wikipedia.org`
уходит тоже — её работу делает ступень WEB.

**Известная цена:** кириллический артист, которого нет в ru-вики, но есть в
en, больше не досматривается вторым проходом и уходит на веб-ступень.
Принято сознательно.

### Ступень WEB — 1 поиск, лениво

Тратится, только если из вики чанков не вышло: статьи нет, либо статья есть,
но ни один чанк не прошёл гейт в `write_bio`.

Один запрос `{artist} musician band biography` через **тот же**
`SearchSources`, что и весь остальной ассистентский стек: junk-URL, спам-хосты,
host-takeover, дедуп, пауза 1.5 с. Дальше — та же лестница гейтов, что уже
работает в нынешнем `widen`: CE по `title+snippet` на входе, fetch выживших
(≤3), CE по телу чанка на `CE_ARTICLE_GATE` перед попаданием в корпус.

Чанк из AudioDB-сида добавляется **только на этой ступени**. Есть вики-статья —
сид не участвует, вики-путь остаётся байт в байт как сейчас.

> Открытое решение, зафиксировано осознанно: веб тратится **лениво**, а не
> всегда. Значит, у артиста со статьёй фасеты, которых в статье нет, останутся
> пустыми. Альтернатива — тратить веб-поиск всегда, обогащая корпус, — это
> одна строчка (`if not chunks` → безусловно). Решать по замеру покрытия
> фасетов «после».

### Фасеты — ретрив по корпусу, а не новые поиски

Механизм `widen` удаляется целиком. Пустой фасет больше не порождает
веб-поиск; вместо этого по **уже собранному** корпусу задаются новые запросы.

1. **Генерация запросов.** Один вызов LLM на всего артиста возвращает JSON:
   на каждый из четырёх фасетов 2–3 переформулировки, с учётом имени артиста.
   Провал парсинга или пустой ответ — падаем на нынешние жёстко зашитые
   строки `FACETS`, они и остаются дефолтом.
2. **Ретрив.** Каждая переформулировка идёт в `HybridRetriever.search` —
   два эмбеддера (dense Octen + learned-sparse MILCO) плюс BM25, слияние RRF,
   переранжирование кросс-энкодером, гейт `CE_CHUNK_GATE`. Ранжирования
   переформулировок сливаются RRF **по рангам**, как это уже сделано для пяти
   граней биографии: вероятности CE несравнимы между разными запросами.
3. **Предложенческий проход остаётся вторым заходом.** Если после (2) не
   выжило ни одного чанка — работает нынешний `facet_chunks`: ранжирование
   ПРЕДЛОЖЕНИЙ с чтением родительских чанков, теми же сгенерированными
   запросами. Он существует не для красоты: на уровне чанков фраза M83
   «named after the galaxy» не находилась вовсе, а происхождение названия
   Daft Punk начинается с «Their name was taken from…» и само по себе
   скорится на 0.14.
4. Промпт фасета — без изменений.

Индекс строится один раз на корпус; `HybridRetriever.extend` уже умеет
дошивать веб-чанки, не переэмбеддя вики-часть.

### Бюджет

- **wiki = 2** — структурно: в `find` ровно два вызова, без циклов.
- **web = 1** — один экземпляр `SearchSources` на весь `build()`, созданный с
  `AgentConfig(max_web_searches=1)`. Его собственный счётчик и дедуп наконец
  начинают работать, потому что экземпляр перестаёт быть одноразовым.

## Побочный выигрыш: контроль текста

`_guard_fallback` снимал проверку `invented`, потому что у агента не было
источника: всё, что он нашёл в вебе, «отсутствует в источнике» по построению.
У веб-чанков источник есть — значит на веб-ветке впервые начинает работать
полный `tq.check(source=ctx, lang=…)`, тот же, что на вики. Отдельная функция
контроля для фоллбэка исчезает вместе с фоллбэком.

## Риски

1. ~~**`exlimit` может не поехать**~~ — снят, проверено живым запросом.
2. **Кириллица без ru-статьи** теряет en-проход.
3. **Покрытие фасетов** может просесть: было до 4 веб-поисков, стало 0.
   Компенсируется генерацией запросов и двумя эмбеддерами по корпусу —
   но это гипотеза, которую проверяет замер, а не факт.
4. **18% артистов** сейчас обслуживает агент. Если новая веб-ступень окажется
   строже него, часть из них останется вовсе без биографии. Это допустимый
   исход (страница просто не показывает блок), но его надо увидеть в цифрах,
   а не узнать от пользователя.
5. **Генерация запросов — лишний вызов LLM на артиста.** Один на все четыре
   фасета, и жёстко зашитая формулировка остаётся первой в каждом списке, так
   что провал модели ничего не ломает. Но в секундах на артиста он виден.

## Верификация

Замер делается на проде и только на проде: `bio_v2` держит модели резидентно
в процессе uvicorn, и любой отдельный процесс (`docker exec python …`) грузит
ВТОРУЮ копию Octen на ту же карту и падает с `CUDA error: out of memory` ещё
на `.to(device)`. Это не гипотеза: первый заход зонда 2026-08-26 упал именно
так, и мёртвый кросс-энкодер сделал замер бесполезным — `article.gate` при
`ce_probabilities() is None` подставляет `[1.0] * len(pool)` и пропускает
всех кандидатов подряд, а `facet_chunks` возвращает пусто для всех фасетов,
из-за чего `widen` отработал 4 раза у каждого из десяти артистов и подвесил
движки (`brave: Suspended`, `duckduckgo: CAPTCHA`).

На карте прода 109 МиБ свободно из 24576 — место под вторую копию моделей не
появится, и зонд в отдельном процессе невозможен в принципе, а не «жаден».
Поэтому замер идёт только in-process, то есть реальным прогоном задачи.
