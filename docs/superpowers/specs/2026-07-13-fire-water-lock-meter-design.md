# Огонёк / Вода — блокировка, метр вклада и краткосрочный сдвиг

**Дата:** 2026-07-13
**Статус:** проектирование
**Скоуп:** бэкенд (сдвиг веса огонька в краткосрок + latest-wins + эндпоинт
состояния) и фронтенд (блокировка кнопок, заполнение иконки, хинт).
**Опирается на:** `docs/superpowers/specs/2026-06-29-fire-wave-recsys-design.md`
(базовая механика огонька/воды уже реализована).

---

## 1. Контекст и цель

Огонёк/вода уже работают: журнал `taste_signals`, эфемерная «волна» (~4ч ×
счётчик треков), депозит в «вайбики» (`H_VIBE_DAYS=2.5`), в острова
(`H_ISLAND_DAYS=30`) и в ранг «любимых» (`H_LIKE_DAYS=90`). Но:

1. Кнопки можно жать бесконечно, состояние никак не отражается в UI и не
   переживает перезаход.
2. Огонёк слишком «долгоиграющий»: 3–5 огоньков в день заметно шумят в общих
   (долгосрочных) рекомендациях.

**Цель.** Сдвинуть вклад огонька в краткосрок (вайбики, полураспад 1 день),
глобально снизить его долгосрочный след, и дать пользователю понятный UX:
одна активная реакция на трек, видимый «остаток заряда» в иконке, честная
разблокировка по прохождении полураспада.

---

## 2. Модель поведения (UX-контракт)

- На каждом треке **не более одной активной реакции**. Нажатие противоположного
  вида **вытесняет** предыдущий (вода поверх огонька → огонёк отменён, и наоборот).
- **Метр (заполнение иконки)** — насколько трек ещё активен в рекомендациях:
  доля `contribution ∈ [0,1]` от свежего сигнала. Иконка активного вида залита
  снизу вверх пропорционально `contribution` (огонёк — оранжевым, вода — синим).
- **Блокировка.** Кнопка активного вида **заблокирована**, пока её
  `contribution > 0.5` (полураспад не прошёл) — и это визуально явно (муteд +
  `cursor:not-allowed` + пояснение в тултипе). Противоположная кнопка **всегда
  доступна** (она вытесняет активную).
- **Разблокировка** — когда `contribution ≤ 0.5` (прошёл период полураспада =
  1 день). После этого кнопку можно нажать снова, что обновляет заряд до 100%.
- **Персист.** Состояние живёт в БД (журнал `taste_signals`) и берётся с бэка по
  `track_id`, поэтому огоньки/вода на треках возвращаются после перезахода.
- **Хинт.** Слева от кнопок — существующий `HintBadge` («i») с текстом:
  «Нажми на огонёк — похожих треков станет больше в рекомендациях, на водичку —
  меньше. Эффект длится несколько дней.»

## 3. Бэкенд

### 3.1 Единый полураспад реакции + метр

```python
H_REACTION_DAYS = 1.0   # полураспад «заряда» огонька/воды: и метр, и вклад в вайбики
```

`contribution(age_days) = 0.5 ** (age_days / H_REACTION_DAYS)`, клампится в
[0,1]. `locked = contribution > 0.5` (т.е. `age < 1 день`). Это чистая
детерминированная функция от `created_at` активного сигнала — единственный
источник правды и для метра, и для влияния на вайбики.

### 3.2 Сдвиг весов (краткосрок ↑, долгосрок ↓)

Правка констант в `stream_service.py`:

| Константа | Было | Стало | Зачем |
|---|---|---|---|
| фаза fire в вайбиках | `H_VIBE_DAYS=2.5` | `H_REACTION_DAYS=1.0` | быстрее гаснет, «вайб дня» |
| `VIBE_FIRE_DEPOSIT` | 1.0 | 0.7 | чуть снизить вклад в вайбик |
| `FIRE_ISLAND_DEPOSIT` | 1.0 | 0.4 | глобально снизить долгосрочный след |
| `FAV_FIRE_W` | 1.0 | 0.5 | огонёк меньше «назначает любимое» |
| фаза water в вайбиках | `H_VIBE_DAYS=2.5` | `H_REACTION_DAYS=1.0` | симметрично огоньку |

Эфемерная «волна» (`FIRE_TIME_MAX_H`, `count_factor`) **не трогается** — это
мгновенный сессионный руль на минуты/часы, отдельный от многодневного метра.
Острова огонёк по-прежнему подпитывает, но слабым депозитом (0.4) на длинном
`H_ISLAND_DAYS` — это незаметный фон, который метр (1 день) не показывает. Так
3–5 огоньков в день формируют «вайб», а не переписывают долгосрочный вкус.

### 3.3 Latest-wins (отмена = вытеснение)

Активная реакция трека = **последний по `created_at` сигнал** для этого трека.
Добавляем чистый хелпер:

```python
def latest_per_track(signals: list[FireSignal]) -> list[FireSignal]:
    """Оставляет по одному (новейшему) сигналу на трек. Реализует «одна активная
    реакция»: вода поверх огонька вытесняет огонёк, повторное нажатие обновляет
    метку времени (без двойного учёта)."""
```

Применяется сразу после парсинга журнала в `next_chunk` (к `all_taste` — глобально,
и к `session_taste` — в рамках сессии) и в эндпоинте состояния. Тогда:
- трек с активной водой **не** учитывается как депозит-огонёк нигде (вайбики,
  острова, «любимые»), и наоборот;
- повторные огоньки на одном треке считаются один раз (свежайший), что заодно
  снижает шум от «много огоньков на один трек».

> Меняется семантика суммирования: тест `test_multiple_fires_same_track_sum`
> обновляется под latest-wins (это осознанная часть редизайна).

### 3.4 Эндпоинт состояния

`GET /api/v1/recommend/taste-signal/state?track_ids=a,b,c` (коллекция —
из JWT). Возвращает по каждому запрошенному треку с активным сигналом:

```json
{ "states": { "<track_id>": { "kind": "fire", "contribution": 0.83, "locked": true } } }
```

Треки без сигналов в ответе опускаются (фронт трактует как `kind=null`).
`kind` берётся из `latest_per_track`; `contribution`/`locked` — из §3.1.

Новый метод БД: `MetadataDB.get_latest_taste_signals(collection_name, track_ids)
-> dict[track_id, (kind, created_at)]` — по одному новейшему ряду на трек
(SQL: оконка/`MAX(id)` group by track_id, фильтр по `track_ids`).

### 3.5 Модели / роуты

- `app/domain/models.py`: `TasteSignalState { kind, contribution, locked }`,
  `TasteSignalStateOut { states: dict[str, TasteSignalState] }`.
- `app/api/routes/recommend.py`: GET-роут из §3.4.
- `POST /taste-signal` не меняется (запись append-only и так реализует latest-wins).

## 4. Фронтенд (`frontend/src/main.jsx`)

### 4.1 Состояние по треку

- При смене `currentTrack` — `GET .../taste-signal/state?track_ids=<id>`; результат
  в локальный стейт `tasteState = { kind, contribution, locked } | null`.
- `postTasteSignal` (уже есть) шлёт запись. `sendTaste(kind)` дополняется:
  - гард: если `tasteState?.kind === kind && tasteState.locked` — no-op (кнопка и так
    `disabled`);
  - **оптимистично**: `setTasteState({ kind, contribution: 1, locked: true })`
    (мгновенная заливка/блокировка активной, обнуление противоположной).

### 4.2 Кнопки

Оборачиваем существующие SVG огонька/воды:
- **Заливка.** Активный вид залит снизу на высоту `contribution`. Реализация:
  `fill` пути через вертикальный `<linearGradient>` с жёсткой границей на
  `offset = 1 - contribution` (SVG y растёт вниз: ниже границы — цвет, выше —
  прозрачно). Огонёк — оранжевый (`--accent`/тёплый), вода — синий. Неактивный вид
  и «пустой» трек — только обводка (как сейчас).
- **Блокировка.** `disabled` когда `kind === thisKind && locked`; визуально —
  `opacity ~0.5` + `cursor:not-allowed`; тултип меняется на «разблокируется, когда
  заряд опустится ≤50% (примерно через сутки)». Противоположная кнопка
  `disabled` только при отсутствии трека (как сейчас).

Живой тик заливки не нужен: за время прослушивания (минуты) `contribution` при
1-дневном полураспаде меняется на доли процента — значение статично на загрузку трека.

### 4.3 Хинт

Перед кнопкой огонька в `.player-actions-row` — `<HintBadge size={16} .../>` с
RU/EN-текстом (RU выше; EN: «Tap fire — more of this in your recs, water — less.
The effect lasts a few days»).

## 5. Тестирование

**Unit (`tests/unit/`):**
- `contribution`/`locked`: 1.0 при age=0, 0.5 при age=1д (граница разблокировки),
  <0.5 за пределами; монотонно убывает.
- `latest_per_track`: вода после огонька → активна вода, огонёк исключён; повтор
  огонька → один сигнал с новейшей меткой.
- вклад в вайбики огонька гаснет по `H_REACTION_DAYS`; вода-штраф — тоже.
- обновление `test_fire_wave.py` под latest-wins.

**Integration (`tests/integration/`):**
- запись `taste-signal` → `GET .../state` отражает `kind/contribution/locked`;
  свежий сигнал `locked=true`, старый (замоканное время) `locked=false`.
- вода поверх огонька в state → `kind=water`.

**Фронт:** верификация лёгкая — `npm --prefix frontend run build` (Docker не
поднимаем).

## 7. Риски

- **Latest-wins меняет суммирование огоньков.** Обновляем затронутый тест; это
  соответствует новой модели «одна активная реакция».
- **Снижение долгосрочного веса** может ослабить острова на холодной библиотеке —
  острова всё равно держатся на дослушиваниях ≥85% (см. базовую спеку §7).
- **Рассинхрон метра.** Метр (1 день) показывает краткосрочный вклад; слабый
  островной след живёт дольше, но незаметен — это сознательно.
