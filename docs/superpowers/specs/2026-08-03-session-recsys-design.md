## 1. Контекст и проблема

«Поток» генерирует последовательность так: долгосрочные острова вкуса (огоньки +
дослушивания ≥85%, медленный learning rate) дают якоря → CLAP-соседи якорей
образуют основной пул → сессия подмешивается с потолком в 50% влияния. Слайдер
«РЕДКОЕ ↔ ЛЮБИМОЕ» управляет только квотой пула «любимых».

Пять наблюдаемых дефектов, подтверждённых по коду:

**1. Ползунок «редкое» не означает «неслышанное».** `liked_share` управляет
исключительно квотой пула «любимых» в `assemble_chunk`
(`stream_service.py:933`). Из основного пула жёстко исключаются лишь дизлайки,
prefetch-буфер и «пол» анти-повтора — последние 10 треков плюс всё за 30 минут
(`_anti_repeat_floor:1374`). Трек, игранный вчера, остаётся полноправным
кандидатом; единственный сдерживающий член `SCORE_W_RECENT = 0.15·exp(−h/24)`
(`:613`, `:928`) через сутки равен **0.055** при разбросе якорного члена ≈0.4 —
практически ноль. Якоря при этом строятся из `island_taste_weights` (`:1127`),
то есть из самых заслушанных треков, и их CLAP-соседи — те же заслушанные.
Отсюда «залипает на одних треках».

**2. Вода — слабый и короткоживущий сигнал.** Штраф `WATER_W = 0.3·cos·decay`
(`:72`, `:922`) против якорного вклада до +0.5. Полностью затухает за 4 часа
(`FIRE_TIME_MAX_H`) или 50 треков сессии (`:1022–1039`). Строится только из
`session_taste` (`:1451`) — новая вкладка стирает воду совсем. В
`negative_track_ids` (`:325`) вода не входит. И главное: `favorite_weights`
(`:1524`) = огоньки + `completion_counts`; воду `latest_per_track` перебивает
только для огоньков, дослушивания не трогает — политый, но заслушанный трек
продолжает выдаваться из liked-квоты.

**3. Длительность прослушивания перебивает явную реакцию.** Событие в
`playback_events` пишется на смене трека независимо от того, была ли реакция.
Политый на третьей минуте четырёхминутный трек даёт `W_MOST = +0.25` и попадает
в `partial_counts`/вайбы; дослушанный — `W_FULL` плюс `completion_counts`, то
есть в «любимые» и острова. Новое событие пересобирает `session_weights` →
волну → якоря, поэтому очередь перетряхивается на переключении трека.

**4. Правило простоя душит фоновое слушание.** `IDLE_STREAK = 5` (`:55`,
`weight_events:193`): после пяти треков подряд без взаимодействия все
последующие события получают вес 0, пока юзер что-нибудь не нажмёт.

**5. Сессии фактически не существует как модели.** `session_id` живёт в
`sessionStorage` вкладки (`frontend/src/main.jsx:493`); константа
`IDLE_RESET_H = 30` (`:119`) описывает поведение, которого во фронте нет.
Переноса сигналов между сессиями нет — новая вкладка стартует холодной от
островов. Веса скипов и реакций — глобальные константы, одинаковые для всех.
Пороги похожести (`NEG_PROXIMITY_THRESHOLD = 0.80`, `ANCHOR_MERGE_THRESHOLD =
0.85`, `VIBE_NEG_SIM = 0.88`) живут в узком хвосте распределения косинусов CLAP
и подбирались вручную.

### Цель

Перенести генерацию последовательности с долгосрочного профиля на сессию;
сделать сигналы честными (реакция перебивает прослушивание, вода реально
дебафает); адаптировать веса под конкретного слушателя; сделать обещание
ползунка выполнимым.

### Принятые решения (резюме)

1. Сессия остаётся вкладкой браузера. Новая вкладка = новый случай
   прослушивания; затухания внутри сессии не меняются.
2. Ползунок: на крайнем «редком» — жёсткий фильтр; в промежуточных положениях —
   настоящая смесь квот свежего и знакомого пулов.
3. Вода не банится навсегда: жёсткое молчание пару суток, но обязана перебивать
   вклад длительности прослушивания.
4. Похожесть CLAP переводится в перцентили распределения по коллекции.
5. Базовая линия слушателя считается на лету, без нового состояния в БД.
6. Прощение скипа — по каждому положительному кластеру отдельно.
7. Правило простоя удаляется полностью.

### Non-goals

Вайбики, autoplay-очередь, ai-playlist, `similar_tracks`, `axis_playlist`,
вкладка «Рекомендации» (`long_term_profile`) — логика не меняется. Вайбы начнут
получать *исправленные* сигналы (см. §2.1), их собственные правила остаются как
есть. Офлайн-кластеризация библиотеки (k-means по CLAP) сознательно отложена:
перцентильной калибровки достаточно, чтобы сессионные кластеры разделялись.

## 2. Фундамент: события → сигналы

### 2.1. Реакция перебивает прослушивание

Огонёк или вода на треке `T` в момент `t` ставит **отсечку**: любое событие
прослушивания `T` с `played_at ≤ t + REACTION_GRACE_SEC` даёт ноль во все
неявные агрегаты — `base_weight`, `completion_counts`, `partial_counts`,
`favorite_weights`, острова, вайбы, вес сессии.

```
REACTION_GRACE_SEC = 30
```

Грейс нужен потому, что событие флашится уже после нажатия, на смене трека
(`main.jsx:636`, `flushListen`).

Правило симметрично для обоих видов реакции: у огонька есть собственная явная
сила, дублировать её дослушиванием нельзя; у воды дослушивание не должно тянуть
трек вверх. Отсечка применяется и к отрицательному неявному весу — «время
прослушивания не влияет» означает буквально не влияет.

Прослушивания `T` **после** момента `t` считаются нормально: раз пользователь
сам включил трек снова, это новый сигнал.

Побочный эффект — устранение перетряхивания очереди при переключении трека, на
который нажали воду: событие приезжает с нулевым весом, профиль не меняется,
повторный запрос чанка возвращает ту же последовательность. Мгновенный рефетч по
самому нажатию (`onStreamSignal('reaction')`, `main.jsx:16357`) сохраняется — он
и должен быть быстрым.

### 2.2. Удаление правила простоя

`IDLE_STREAK`, счётчик `passive_streak` и обнуление веса в `weight_events`
(`stream_service.py:193–216`) удаляются. Колонка `interacted` в
`playback_events` продолжает записываться (дёшево, может пригодиться), но
рекомендатель её больше не читает. `PlaybackSignal.interacted` остаётся в
датаклассе для совместимости чтения из БД.

### 2.3. Базовая линия слушателя и адаптивные веса

Считается на лету из тех же `LONG_TERM_EVENT_CAP = 2000` событий, что уже
загружаются в `next_chunk`. Учитываются только события с `influence = True` и
известной длительностью.

Метрики:

| метрика | определение |
|---|---|
| `p_skip` | доля прослушиваний, попадающих под `is_skip` |
| `p_full` | доля прослушиваний с ratio ≥ `FULL_RATIO` |
| `p_react` | (огоньки + воды) / число событий |

Множители:

```
m_skip  = clamp( (P_SKIP_REF  / max(p_skip,  EPS)) ** 0.5, 1/ADAPT_CAP, ADAPT_CAP )
m_full  = clamp( (P_FULL_REF  / max(p_full,  EPS)) ** 0.5, 1/ADAPT_CAP, ADAPT_CAP )
m_react = clamp( (P_REACT_REF / max(p_react, EPS)) ** 0.5, 1/ADAPT_CAP, ADAPT_CAP )

P_SKIP_REF  = 0.25
P_FULL_REF  = 0.50
P_REACT_REF = 0.08
ADAPT_CAP   = 2.0
EPS         = 1e-3
```

Корень смягчает реакцию на выбросы; `clamp` — кэп, чтобы веса не улетали.
Смысл: у слушателя, который почти не скипает, скип весит до 2×, у хронического
скипальщика — 0.5×. Симметрично для дослушиваний: если дослушивается всё
подряд, дослушивание малоинформативно. Реакции нормируются по тому, как часто
пользователь вообще жмёт кнопки.

Холодный старт (защита от болтанки на малой истории):

```
ramp = clamp((n_events − BASELINE_MIN) / (BASELINE_FULL − BASELINE_MIN), 0, 1)
m_eff = 1.0 + (m − 1.0) · ramp

BASELINE_MIN  = 50
BASELINE_FULL = 200
```

Применение: `m_skip` умножает `W_SKIP`, `m_full` — `W_FULL` и `W_MOST`,
`m_react` — вес огонька и воды в кластерах сессии (§4). Долгосрочные острова и
«любимые» множителей **не** используют — они по замыслу медленные, а адаптация
предназначена для сессионного слоя.

## 3. Вода

| аспект | сейчас | становится |
|---|---|---|
| часы жизни | 4 ч ИЛИ 50 треков сессии | период полураспада 1 день |
| область действия | только своя сессия | глобально по коллекции |
| сам трек | штраф −0.3 к скору | жёстко не выдаётся `WATER_MUTE_DAYS`, дальше затухающий штраф |
| дослушивание трека | считается как обычно | обнуляется отсечкой §2.1 |
| «любимые» / острова / якоря | трек остаётся | выпадает (та же отсечка) |
| соседи по CLAP | `0.3·cos·decay` | член `repulsion` (§4.6), `k = 1.0` |

```
H_WATER_DAYS    = 1.0   # период полураспада заряда воды
WATER_MUTE_DAYS = 2.0   # жёсткое молчание трека
WATER_TAIL_DAYS = 5.0   # к этому возрасту штраф соседям обнуляется
water_charge(age_days) = 0.5 ** (age_days / H_WATER_DAYS)
```

Трек с активной водой возрастом < `WATER_MUTE_DAYS` попадает в
`hard_excluded` наравне с дизлайками. После этого возвращается в общий пул с
быстро тающим штрафом через `repulsion`.

Повторный огонёк на треке снимает всё сразу — `latest_per_track` уже реализует
«одна активная реакция на трек».

Огонёк сохраняет свои двойные часы (`fire_time_factor` × `fire_count_factor`) —
это эфемерный руль волны, он и должен быть коротким. У воды теперь собственный
таймер; в коде это две отдельные функции с говорящими именами, а не одна с
флагом.

## 4. Сессионный движок

### 4.1. Состав сессии

События с текущим `session_id`. Вес события = базовый вес × адаптивный
множитель (§2.3), с отсечкой по реакциям (§2.1). Затухания внутри сессии
остаются нынешними (`H_IMPLICIT_DAYS`, `H_REACTION_DAYS`).

- **Положительные участники**: треки с положительным весом + огоньки
  (`FIRE_BASE · m_react · fire_time_factor · fire_count_factor`).
- **Отрицательные участники**: скипы после прощения (`|W_SKIP| · m_skip`) +
  воды (`WATER_BASE · m_react · water_charge`).

### 4.2. Кластеры притяжения и отталкивания

Обе стороны прогоняются через существующий `merge_anchors`, но порог задан в
перцентилях (§5), а не в сыром косинусе. Результат — `C⁺` (пул, к которому
тянемся) и `C⁻` (от которого отталкиваемся). Вес кластера — сумма весов
участников.

```
CLUSTER_MERGE_PCT = 0.985   # эквивалент нынешнего ANCHOR_MERGE_THRESHOLD = 0.85
TOP_POSITIVE_CLUSTERS = 5   # столько центроидов уходит в Qdrant
TOP_NEGATIVE_CLUSTERS = 5   # столько участвует в repulsion
```

Запросы к Qdrant идут вокруг **центроида кластера**, а не вокруг вектора
трека-представителя, как сегодня (`pool_anchor_candidates:698`). Центроид —
нормированное взвешенное среднее unit-векторов участников; `query_points`
принимает произвольный вектор, отдельная точка в коллекции не нужна.

### 4.3. Прощение скипа

Для каждого скипа сессии ищется ближайший положительный кластер с
`sim_pct ≥ FORGIVE_SIM_PCT`. В каждом кластере первый такой скип прощается
(вес 0). Как только в том же кластере появляется второй, засчитываются оба,
включая ретроактивно прощённый. Скип, не похожий ни на один `C⁺`, засчитывается
всегда.

```
FORGIVE_SIM_PCT = 0.97   # верхние 3% похожести по меркам коллекции
```

Сценарий: не нравится конкретная песня — прощаем; не нравится весь рок —
не прощаем.

Прощение вычисляется **до** построения `C⁻`, то есть прощённый скип не попадает
в отрицательные кластеры вовсе.

### 4.4. Перенос между сессиями

Новая вкладка стартует не с нуля. Источник переноса — предыдущая сессия
(та, чьё последнее событие ближе всего предшествует первому событию текущей):

- последние `CARRYOVER_TAIL = 10` значащих событий,
- огоньки и воды за последние `CARRYOVER_SIGNAL_DAYS = 2` дня.

```
CARRYOVER_W          = 0.4   # множитель веса перенесённых участников
CARRYOVER_MAX_AGE_D  = 3.0   # старше — перенос не применяется
CARRYOVER_FADE_SIG   = 8     # столько своих сигналов снимают перенос полностью
```

Перенесённые участники входят в те же `C⁺`/`C⁻` с коэффициентом `CARRYOVER_W`
и линейно обнуляются по мере накопления собственных сигналов сессии. Если
предыдущая сессия закончилась больше `CARRYOVER_MAX_AGE_D` назад, переноса нет
— вкус мог поменяться.

Перенос переносит **звучание**, а не конкретные треки: анти-повтор к
перенесённым трекам применяется на общих основаниях.

### 4.5. Роль долгосрочного профиля

Острова остаются, но только как затравка холодного старта:

```
w_long = max(LONG_TERM_FLOOR, 1 − n_session_signals / LONG_TERM_FADE)

LONG_TERM_FLOOR = 0.15
LONG_TERM_FADE  = 6
```

На первом треке сессии долгосрочный профиль правит целиком; к 5–6 сигналам
сжимается до пола 0.15, дальше ведёт сессия. Пол не нулевой намеренно: сессия,
свалившаяся в странный угол, должна иметь чем оттуда выбраться.

Островные якоря входят в `C⁺` с весом × `w_long`; сессионные кластеры — с
весом × `(1 − w_long)`. Одна общая нормировка, один пул притяжения.

Константы `SESSION_BLEND_MAX`, `SESSION_SIGNALS_SATURATION`,
`SESSION_ANCHOR_BOOST`, функции `session_blend_weight` и
`union_anchor_weights` удаляются — их роль полностью берёт на себя `w_long`.

### 4.6. Скор кандидата

```
affinity  = max по C⁺ ( ŵ⁺ · sim_pct(кандидат, центроид) )
repulsion = max по C⁻ ( ŵ⁻ · sim_pct(кандидат, центроид) · k )
            k = REPEL_K_WATER для водяных кластеров
            k = REPEL_K_SKIP  для скиповых

score = W_AFFINITY·affinity − W_REPULSION·repulsion
      + W_AXIS·axis_match + W_NOVELTY·novelty − W_RECENT·recency

W_AFFINITY    = 0.50
W_REPULSION   = 0.35
W_AXIS        = 0.20
W_NOVELTY     = 0.10
W_RECENT      = 0.15
REPEL_K_WATER = 1.0
REPEL_K_SKIP  = 0.45
```

`ŵ` — веса кластеров, нормированные так, что максимальный равен 1.

Отталкивание от воды сильнее, чем от скипов. Водяная часть `repulsion` — это и
есть штраф соседям политого трека из §3; отдельного механизма
(`water_proximity`, `WATER_W`) больше нет. Жёсткое двухдневное молчание самого
политого трека — исключение из пула, а не член скора.

### 4.7. Что удаляется

`detect_pivot`, `pivot_anchors`, `session_wave_vector`, `_wave_alignment`,
`rank_effective_anchors` и связанные константы (`WAVE_MIN_SIGNALS`,
`PIVOT_WINDOW`, `PIVOT_SKIPS`, `PIVOT_WATERS`, `PIVOT_WATER_WINDOW_MIN`,
`PIVOT_SIM_CEIL`).

Разворот «резко сменить пластинку» теперь получается сам: очередь скипов лепит
тяжёлый `C⁻`, который отталкивает всю эту область скором. От старого пивота
сохраняется единственная деталь — расширение случайной доли свежего пула при
серии скипов (§6):

```
если ≥ SKIP_BURST_N скипов среди последних SKIP_BURST_WINDOW событий сессии
    stratified_share = max(FRESH_STRATIFIED_SHARE, SKIP_BURST_STRATIFIED_SHARE)

SKIP_BURST_N      = 3
SKIP_BURST_WINDOW = 5
SKIP_BURST_STRATIFIED_SHARE = 0.5
```

`n_session_signals`, от которого зависят `w_long` (§4.5) и снятие переноса
(§4.4), — это число событий сессии с ненулевым весом (после отсечки §2.1 и
прощения §4.3) плюс число огоньков и вод сессии.

`session_adaptation` («подстроились под твой вайб») остаётся.

## 5. Перцентильная калибровка CLAP

Косинусы CLAP в личной библиотеке лежат в узком диапазоне, из-за чего абсолютные
пороги (0.80 / 0.85 / 0.88) приходится подбирать под конкретную коллекцию, а
разница между «похоже» и «очень похоже» теряется.

**Построение таблицы.** Один раз на коллекцию: `CALIB_SAMPLE = 512` случайных
треков (скролл с `with_vectors=["clap"]`), матрица попарных косинусов
(512×512 ≈ 131k значений, одна операция numpy), из неё 101 квантиль
(перцентили 0..100). Хранится в `collection_settings` как JSON вместе со
штампом числа треков и временем построения.

**Использование.** `sim_pct(cos) ∈ [0, 1]` — линейная интерполяция по таблице,
то есть «насколько эта пара похожа по меркам именно этой библиотеки». Ниже
нулевого квантиля → 0, выше сотого → 1.

**Инвалидация.** Пересчёт, если число треков изменилось более чем на
`CALIB_DRIFT = 10%` или таблице больше `CALIB_TTL_DAYS = 7` дней. Проверка
дешёвая — `qdrant.count` уже вызывается в `next_chunk`.

**Деградация.** Если таблицы нет и построить её не удалось (Qdrant недоступен,
в коллекции меньше 32 треков), `sim_pct` возвращает сырой косинус,
приведённый к [0, 1] как `(cos + 1) / 2`, и в диагностику пишется
`calibration: "raw"`. Рекомендатель работает, просто грубее.

**Переезд порогов:**

| было | стало |
|---|---|
| `ANCHOR_MERGE_THRESHOLD = 0.85` | `CLUSTER_MERGE_PCT = 0.985` |
| `VIBE_NEG_SIM = 0.88` | без изменений (вайбы не трогаем) |
| `NEG_PROXIMITY_THRESHOLD = 0.80` | `EXPLORE_NEG_PCT = 0.95` |
| — | `FORGIVE_SIM_PCT = 0.97` |
| `ISLAND_MERGE_THRESHOLD = 0.80` | без изменений (профиль не трогаем) |

Начальные значения перцентилей подобраны так, чтобы на типичной библиотеке
воспроизводить нынешнее поведение; после бэкфилла (§9) сверяем по диагностике
размеры кластеров и правим при необходимости.

## 6. Ползунок и пулы

Направление ползунка не меняется: слева РЕДКОЕ (`liked_share = 0.0`), справа
ЛЮБИМОЕ (`liked_share = 1.0`), дефолт 0.3.

**Свежий трек** = не игрался никогда ИЛИ последнее воспроизведение старше
`FRESH_WINDOW_DAYS = 30`.

Два пула вместо трёх (`anchor` / `explore` / `liked`):

**Свежий пул.** Только свежие треки, ранжированные скором §4.6. Наполняется в
два захода:
1. свежие среди CLAP-соседей центроидов `C⁺` (расширенный `k`,
   `FRESH_FETCH_K = 150` на центроид);
2. если квота не добралась — стратифицированная случайная выборка по осям
   (существующий `stratify_explore`) из `light_points`, отфильтрованная по
   свежести и ранжированная по `axis_match`.

`FRESH_STRATIFIED_SHARE = 0.25` свежих слотов **всегда** отдаётся
стратифицированной выборке — страховка от фильтр-пузыря (роль нынешнего
explore-пула). При серии скипов доля поднимается до
`SKIP_BURST_STRATIFIED_SHARE` (§4.7). Кандидат из стратифицированной выборки
отбрасывается, если он ближе `EXPLORE_NEG_PCT` к любому центроиду `C⁻` — это
наследник нынешней проверки `NEG_PROXIMITY_THRESHOLD`: случайный выбор не
должен приводить туда, откуда пользователь только что ушёл.

**Знакомый пул.** Соседи центроидов `C⁺` и «любимые», без ограничения по
свежести.

**Квоты.**

```
fresh_slots = round(n · (1 − liked_share))
familiar_slots = n − fresh_slots
```

Крайние положения — жёсткие обещания:

- `liked_share == 0`: только свежее. Пул сух → **короткий чанк** и
  `diagnostics.fresh_exhausted = true`; ничего слышанного за последний месяц не
  подмешивается.
- `liked_share == 1`: только знакомое/любимое — но это **мягкое** обещание:
  если знакомый пул пуст (свежий аккаунт, где всё неслушанное), чанк добирается
  свежим, а не возвращается коротким. Асимметрия намеренная: жалоба была на
  «редкое» подсовывающее слышанное; в обратную сторону недобор хуже примеси.
- Промежуточные: обе квоты настоящие; если один пул сух, второй добирает.

**Что остаётся неизменным:** «пол» анти-повтора (`_anti_repeat_floor` —
последние 10 треков + 30 минут) действует при любом положении ползунка — кроме
выборки «любимых»: там «последние 10 сыгранных» на небольшой истории означает
«всё, что юзер вообще слышал», а любимые по определению слышаны. Их ротацию
задаёт собственный `LIKED_COOLDOWN_H = 8`. Правила
чередования (≤2 подряд из одного пула, ≤2 подряд одного артиста, штраф за
повтор артиста) переносятся в новую сборку без изменений.

**Проходы добора.** Проход 2 «relax» (замкнулся круг — разрешаем уже
слышанное в сессии) и проход 3 «fallback» (играем наименее свежее, лишь бы
поток не был пуст) сохраняются, но применяются **только к знакомым слотам**.
Свежие слоты не добираются ни relax, ни fallback: свежесть — это обещание, а
не предпочтение. Следовательно при `liked_share == 0` оба прохода не
запускаются вовсе.

## 7. Раскладка по файлам

`stream_service.py` — 2157 строк; добавлять туда ещё пласт нельзя. Новый пакет
`app/services/stream/` (конвенция существующих подпакетов `ai_tasks/`,
`fact_relations/`, `lyric_gems/`):

| файл | ответственность | зависимости |
|---|---|---|

`signals.py` появился при реализации: `baseline`/`session`/`pools` нуждаются в
`PlaybackSignal`, `is_skip`, `merge_anchors`, и без общего низа они замкнулись бы
в цикл со `stream_service`. Это нижний слой без зависимостей от Qdrant и SQLite.

`stream_service.py` остаётся оркестратором `next_chunk` и держит нетронутое:
`long_term_profile`, `similar_tracks`, `axis_playlist`,
`vibe_album_suggestions`, `current_vibes` и весь вайб-слой. Публичные имена,
которые импортируют `app/api/routes/recommend.py`, `recsys_ai_service.py` и
существующие тесты, ре-экспортируются из `stream_service` — внешние импорты не
ломаются.

Тяжёлые импорты (`numpy` уже на верхнем уровне `stream_service`, остаётся так)
— без изменений; новые модули не тянут `torch`/`gliner2`, так что конфтестовые
заглушки не затрагиваются.

### Диагностика

В `diagnostics` добавляются: `baseline` (три множителя + `n_events`),
`clusters` (`{positive: [...], negative: [...]}` с весами и размерами),

`fresh_pool`, `fresh_exhausted`, `forgiven_skips`. Удаляются: `w_session`,
`anchors`, `wave`, `pivot`, `n_water`.

**`scripts/backfill_clap_calibration.py`** (конвенция `scripts/backfill_*`):

python -m scripts.backfill_clap_calibration --all --dry-run

Идемпотентен: без `--force` пропускает коллекции с актуальной таблицей.
Печатает по коллекции число треков, размер выборки и ключевые квантили
(p50 / p95 / p97 / p98.5) — по ним сразу видно, попадают ли пороги §5 в
осмысленное место, или их надо править.

**Порядок выкатки** (после мержа в `genius-addition` и зелёного
`pytest tests/unit`):

1. `ivan@192.168.0.168`: `git pull` в рабочей копии ветки `genius-addition`.
2. `docker compose up -d --build` — пересборка образа `musix`.
3. `docker compose logs -f musix` — дождаться готовности lifespan.
4. `docker compose exec musix python -m scripts.backfill_clap_calibration --all`
5. Сверить напечатанные квантили с порогами §5, при необходимости поправить

6. Прод-зонд: одна сессия из ~10 треков, снять `diagnostics` первого и

## 10. Открытые риски

**Свежий пул может быть пуст на маленькой библиотеке.** Пользователь с 200
треками, слушающий каждый день, за месяц перебирает всё. Крайнее положение
ползунка тогда честно отдаёт короткий чанк и флаг — это осознанный выбор
(обещание важнее непустоты), но фронту стоит показать подсказку. Если на проде
окажется больно, следующий шаг — сжимать окно свежести (30 → 14 → 7 дней) с
явной пометкой в диагностике, а не молча подмешивать слышанное.

**Начальные перцентильные пороги — гипотеза.** Проверяются на шаге 5 выкатки по
напечатанным квантилям. Ошибка порога проявится как слишком крупные (всё в
одном кластере) или слишком мелкие (каждый трек — свой кластер) `C⁺`; и то и
другое видно в `diagnostics.clusters`.

**Адаптивные множители на малой истории.** Прикрыто рампой 50→200 событий, но
пользователь с ровно 60 событиями, из которых 55 — скипы, получит
`m_skip ≈ 0.5` уже на четверти силы. Приемлемо: это ослабление сигнала, а не
усиление, худший случай — рекомендатель чуть медленнее учится.
